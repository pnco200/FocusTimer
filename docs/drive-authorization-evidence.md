## Authoritative guarantees and their limits

| Accessed source | Behavior relied upon | Limit of the evidence |
| --- | --- | --- |
| [Choose Drive API scopes](https://developers.google.com/workspace/drive/api/guides/api-specific-auth), “Drive API scopes” and “Benefits of the Drive file scope” | `https://www.googleapis.com/auth/drive.file` is recommended and non-sensitive; access is per-file, for app-created/opened or explicitly shared files. It supports Drive REST resources. | This does not enumerate what “app” means for inherited per-file grants across different OAuth client IDs, or promise that selecting a folder grants every existing/future descendant. Broad `drive`, `drive.readonly` and metadata scopes are not part of this proposal. |
| [Cross-client Identity](https://developers.google.com/identity/protocols/oauth2/cross-client-identity), “Cross-client authorization goals” and “Cross-client access tokens” | Each component has its own client ID; a scope grant to a project client signals trust in the whole application. Existing consent can authorize other reliably identified clients. Web, desktop and mobile clients are included. | Scope-consent reuse is documented; the required Drive corpus-grant and search-visibility semantics are not explicitly specified here. Treating shared project membership as sufficient proof would add an assumption. |
| [Drive files resource](https://developers.google.com/workspace/drive/api/reference/rest/v3/files), `isAppAuthorized` | This output field indicates whether the requesting app created or opened a file. | It is useful recorded evidence for successful metadata reads. It does not make a failed metadata read distinguish missing files from unavailable grants, or prove another client's access. |
| [Integrate Google Picker into web apps](https://developers.google.com/workspace/drive/picker/guides/web-picker), “Display the Google Picker” | Picker's Drive App ID is the Cloud project number and is supplied with the OAuth access token. | Project-number binding is supporting evidence for an app-level model, not an explicit cross-client corpus guarantee. A Picker rescue of one file is a different experiment from automatic rediscovery. |
| [Drive error handling](https://developers.google.com/workspace/drive/api/guides/handle-errors), `authError`, `appNotAuthorizedToFile`, `notFound` | Invalid/expired tokens and missing scope authorization can produce authorization failures; per-file app authorization can fail separately. A 404 can mean missing read access or a nonexistent file. | A failed B read cannot establish that A's file was deleted. Retain identity and bytes locally; do not recreate a bound root or broaden scope. |

These remain separate facts: **scope granted**, **file authorized for this requesting application**, **current account permitted**, and **file returned by enumeration**. The live evidence now includes cross-client descriptor inspection, segment listing and bounded segment reads, with exact retained-byte verification where applicable. No inference from consent, a known root ID or project membership is needed for those observed results.

For account context, [`about.get`](https://developers.google.com/workspace/drive/api/reference/rest/v3/about/get) explicitly accepts `drive.file`; request only `fields=user(permissionId)`. The [`User.permissionId` field](https://developers.google.com/workspace/drive/api/reference/rest/v3/User) identifies the user in Drive permission resources. Use it to pin the observed Drive user without requesting email/profile access. It does not identify the OAuth application/client or prove project membership. Export correlation confirms two distinct account values: matching corpus-account values across positive tests and a different value for the negative control, using the same FG1U client (E02 #30–41). Actual identifiers remain private in the attachments; production account pinning remains required.

## Browser authorization and deferred native requirements

[GIS token model](https://developers.google.com/identity/oauth2/web/guides/use-token-model), “Work with tokens” and “Token expiration”: initialize a web token client, obtain tokens through a user gesture, check granted scopes, and call Google APIs with REST/CORS. Tokens are short-lived; renewal after expiry requires a user-driven request. This supports a backend-free browser experiment; it does not support assuming a browser refresh token or unattended closed-PWA synchronization. Keep access tokens in memory and use the Authorization header. Exclude them from local experiment evidence, URLs, exports, service-worker caches and logs.

[GIS JavaScript reference](https://developers.google.com/identity/oauth2/web/reference/js-reference), `TokenClientConfig`: `include_granted_scopes` defaults to true; false limits the new token to requested scopes. For the scope proof, explicitly request only `drive.file`, set `include_granted_scopes: false`, and require the returned `scope` set to match. A token carrying historical broad Drive grants invalidates the narrow-scope result. Record scope strings and sanitized outcomes, never tokens. Obtain independent tokens for A and B rather than reusing A's token.

[Desktop OAuth](https://developers.google.com/identity/protocols/oauth2/native-app), “Create authorization credentials,” PKCE and “Token revocation”: future desktop public clients need the system browser, a supported redirect, fresh PKCE verifier/challenge with S256, and appropriate secure token storage. A shipped secret cannot remain confidential, and native refresh behavior cannot be assumed for GIS. **Native is DEFERRED / NOT IN CURRENT WEB V1 SCOPE.** If it becomes a product target, its actual official OAuth registration must prove discovery/read/publish interoperability with the web corpus and other shipping clients before its own release. No native result is supplied or required to release the current web product.

The documentation describes project-grant/token revocation with possible propagation delay. The user confirmed correct-account revocation/reconsent separately outside these exports. E02 #33–34 instead records alternate-account revoke/callback, followed by successful corpus-account authorization/discovery/inspection at #36–41. Keep these sources distinct; neither a callback without status nor the outside-capture result establishes the HTTP response of an old revoked token or native behavior.

The live results distinguish discovery without a locator from subsequent root/descriptor/segment access. Preserve that distinction and the two observed directions' comparison limits in production acceptance. Reconnect still must surface zero, multiple, incomplete or unreadable candidates without automatically creating/electing a root. Do not generalize the tested web registrations to every future registration.

For follow-up runs, capture only synthetic payloads, registration aliases/types, granted scopes, safe status/reason, candidate counts and byte-comparison results; exclude credentials and private history. Native remains a future native-client gate, never an open dependency of this Web/PWA v1 decision.

No reported web operation failed the narrow-scope interoperability requirement. If an actual shipping web configuration later fails it, preserve the exact failed operation and scope/account context rather than broadening scope or changing storage automatically. The present live evidence supports the report's **GO WITH CHANGES** recommendation; remaining work is concrete web adapter implementation and acceptance, not waiting for hypothetical native registrations.

## Provider eligibility caveat discovered in current primary documentation

[Drive API Terms, “Customer implementation”](https://developers.google.com/workspace/drive/api/terms) lists “Backup of user or app content from a developer’s app or project to Drive” among uses requiring Google's express prior written consent. The [Workspace developer policy, “Appropriate access to and use of Google Drive Scopes”](https://developers.google.com/workspace/workspace-api-user-data-developer-policy) also lists that category. Whether Focus Timer's use is classified this way, or qualifies under another approved use, was not established. This is retained context from the original documentation research, not a determination about Focus Timer's eligibility or a new approval/architecture gate introduced by this technical reassessment. The Web/PWA v1 transport recommendation and its concrete remaining implementation obligations are stated in the feasibility report; live OAuth/API results do not decide provider-policy classification.
