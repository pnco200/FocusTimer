# Google Drive narrow-scope authorization evidence

Researched 2026-10-18 against the current authoritative pages linked below. Authority for this phase remains SPEC §§22–24,36 and `src/web/sync-transport.ts`; the prior implementation/review, IndexedDB and asynchronous-runner reports were read first. This is an isolated feasibility record, with no production adapter, authorization integration or sync UI.

**Disposition: `drive.file` remains an unproven candidate, not a rejected scope and not an approved architecture choice.** The reviewed official documentation establishes shared scope consent across official project clients. It does not explicitly establish the exact required per-file discovery/read behavior for files created by each separate official OAuth client, including after revocation and reauthorization. No authenticated Google request was executed for this note. Documentation evidence must not be reported as a passing live experiment.

## Authoritative guarantees and their limits

| Accessed source | Behavior relied upon | Limit of the evidence |
| --- | --- | --- |
| [Choose Drive API scopes](https://developers.google.com/workspace/drive/api/guides/api-specific-auth), “Drive API scopes” and “Benefits of the Drive file scope” | `https://www.googleapis.com/auth/drive.file` is recommended and non-sensitive; access is per-file, for app-created/opened or explicitly shared files. It supports Drive REST resources. | This does not enumerate what “app” means for inherited per-file grants across different OAuth client IDs, or promise that selecting a folder grants every existing/future descendant. Broad `drive`, `drive.readonly` and metadata scopes are not part of this proposal. |
| [Cross-client Identity](https://developers.google.com/identity/protocols/oauth2/cross-client-identity), “Cross-client authorization goals” and “Cross-client access tokens” | Each component has its own client ID; a scope grant to a project client signals trust in the whole application. Existing consent can authorize other reliably identified clients. Web, desktop and mobile clients are included. | Scope-consent reuse is documented; the required Drive corpus-grant and search-visibility semantics are not explicitly specified here. Treating shared project membership as sufficient proof would add an assumption. |
| [Drive files resource](https://developers.google.com/workspace/drive/api/reference/rest/v3/files), `isAppAuthorized` | This output field indicates whether the requesting app created or opened a file. | It is useful recorded evidence for successful metadata reads. It does not make a failed metadata read distinguish missing files from unavailable grants, or prove another client's access. |
| [Integrate Google Picker into web apps](https://developers.google.com/workspace/drive/picker/guides/web-picker), “Display the Google Picker” | Picker's Drive App ID is the Cloud project number and is supplied with the OAuth access token. | Project-number binding is supporting evidence for an app-level model, not an explicit cross-client corpus guarantee. A Picker rescue of one file is a different experiment from automatic rediscovery. |
| [Drive error handling](https://developers.google.com/workspace/drive/api/guides/handle-errors), `authError`, `appNotAuthorizedToFile`, `notFound` | Invalid/expired tokens and missing scope authorization can produce authorization failures; per-file app authorization can fail separately. A 404 can mean missing read access or a nonexistent file. | A failed B read cannot establish that A's file was deleted. Retain identity and bytes locally; do not recreate a bound root or broaden scope. |

These are separate facts: **scope granted**, **file authorized for this requesting application**, **current account permitted**, and **file returned by enumeration**. A successful consent dialog, known file ID, `isAppAuthorized` from A, or successful B read of only the root cannot substitute for B's discovery and exact reads of the descriptor and segments.

For account context, [`about.get`](https://developers.google.com/workspace/drive/api/reference/rest/v3/about/get) explicitly accepts `drive.file`; request only `fields=user(permissionId)`. The [`User.permissionId` field](https://developers.google.com/workspace/drive/api/reference/rest/v3/User) identifies the user in Drive permission resources. It can pin and compare the observed Drive user across experiment requests without requesting email/profile access. It does not identify the OAuth application/client or prove project membership; retain that registration evidence separately. This field's usefulness across the required reconnect/client scenarios still needs live observation.

## Browser and future native authorization constraints

[GIS token model](https://developers.google.com/identity/oauth2/web/guides/use-token-model), “Work with tokens” and “Token expiration”: initialize a web token client, obtain tokens through a user gesture, check granted scopes, and call Google APIs with REST/CORS. Tokens are short-lived; renewal after expiry requires a user-driven request. This supports a backend-free browser experiment; it does not support assuming a browser refresh token or unattended closed-PWA synchronization. Keep access tokens in memory and use the Authorization header. Exclude them from local experiment evidence, URLs, exports, service-worker caches and logs.

[GIS JavaScript reference](https://developers.google.com/identity/oauth2/web/reference/js-reference), `TokenClientConfig`: `include_granted_scopes` defaults to true; false limits the new token to requested scopes. For the scope proof, explicitly request only `drive.file`, set `include_granted_scopes: false`, and require the returned `scope` set to match. A token carrying historical broad Drive grants invalidates the narrow-scope result. Record scope strings and sanitized outcomes, never tokens. Obtain independent tokens for A and B rather than reusing A's token.

[Desktop OAuth](https://developers.google.com/identity/protocols/oauth2/native-app), “Create authorization credentials,” PKCE and “Token revocation”: desktop registrations are public clients. Use the system browser, a platform-supported redirect (desktop loopback where appropriate), a fresh PKCE verifier/challenge per authorization, and S256. A shipped secret cannot remain confidential. Native refresh tokens require appropriate secure storage; their availability does not transfer to GIS browser clients. Revocation removes project scope grants and invalidates tokens across its clients, with possible propagation delay. The reviewed page does not specify whether a particular Drive per-file grant becomes reusable after reauthorization. Test that separately. Mobile registrations require their current platform-specific guidance and their own matrix rows; a desktop test cannot certify future mobile clients.

## Cross-client test matrix and acceptance

All rows below are **NOT RUN**. There are no supplied Focus Timer project/client IDs, user-authorized official-client tokens, or native registration evidence in the selected managed runtime. Its current readiness report exposes no secrets, runtime variables or outbound identities. The configured HTTP destination list does not include Google's OAuth/Drive API hosts; its reported enforcement state was unknown. A connected Drive app, if available, would use that connector's registration and cannot prove Focus Timer's selected scope or client matrix.

| Scenario | Required independent observation |
| --- | --- |
| Web A creates root, descriptor and segments | Scope-only A token; retain generated file IDs and exact synthetic descriptor/segment bytes. A enumerates and reads its complete corpus. |
| Web B reconnects, same registration, clean browser state | Obtain B's own token for the same account. With no root locator, discover candidates, then enumerate/read every artifact exactly; separately test known-ID recovery. |
| Web B uses a different official web client ID in the same project | Repeat clean discovery and known-ID reads; B publishes a distinct segment, and A discovers/reads it. No token sharing or Picker grants to hide a failure. |
| Official desktop/native client, same project | Independently complete public-client OAuth. Discover/read A and B artifacts; publish new content, then verify it from both web IDs. Repeat for every planned native registration. |
| Reinstall/storage clear without revocation | Erase local locator/token state; use a fresh authoring installation identity. Rediscover the existing remote corpus and compare bytes. |
| Revoke, wait for rejection, reauthorize | Observe old-token failure; obtain scope-only tokens again and repeat the complete bidirectional discovery/read checks. Record whether explicit file authorization is required. |
| Wrong account and independent project controls | Do not send retained publication bytes before account validation. Missing/inaccessible old root must remain unresolved. A separate project is not an official-client success case. |

For every pair, test both **discovery without a retained locator** and **read by retained IDs**. Read the descriptor and each child's exact bytes and validate their dataset/segment identities; record the complete candidate count and all pages, not just the first match. A scope-only read of one selected file is not a corpus proof. Reconnect must surface zero, multiple, incomplete or unreadable candidates without creating/electing a root automatically.

Capture only synthetic payloads, client aliases/platform types, project/client registration evidence, granted scopes, request method/route without secrets, status/reason, candidate counts and exact-byte comparison results. Publish no actual user history. A live passing web A/B row establishes only those tested registrations and conditions. A future unregistered native client remains an open gate.

If any required official client cannot discover/read the shared corpus using only `drive.file`, stop that transport decision and report the exact failing pair and request. Do not request a broader scope or switch to hidden app data as an automatic fallback. If execution is unavailable, preserve **unproven** rather than report **impossible** or **passed**.

## Provider eligibility caveat discovered in current primary documentation

[Drive API Terms, “Customer implementation”](https://developers.google.com/workspace/drive/api/terms) lists “Backup of user or app content from a developer’s app or project to Drive” among uses requiring Google's express prior written consent. The current [Workspace developer policy, “Appropriate access to and use of Google Drive Scopes”](https://developers.google.com/workspace/workspace-api-user-data-developer-policy) also lists that category. Whether Focus Timer's proposed use is classified this way, or qualifies under another approved use, was not established. This note makes no categorical finding about synthetic feasibility experiments. Provider eligibility needs resolution before committing to deployment; a technically working scope does not establish that eligibility.
